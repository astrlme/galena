---
title: Self-hosting on AWS
description: Deploy Galena into your own AWS account, from an empty account to a live status page.
---

Galena deploys with the AWS CDK, from your machine with `galena deploy` or from a GitHub Actions
workflow that signs in to AWS with OIDC. Everything runs in your account, background jobs
included, so AWS is the only account you need.

## Before you start

1. **An AWS account that holds nothing but Galena.** Sign in as root once, turn on MFA, and stop
   using root. Create an IAM Identity Center user with administrator access, and set a monthly
   budget with email alerts.
2. **The AWS CLI**, signed in as that user with `aws configure sso`. `aws sts get-caller-identity`
   should name the account.
3. **Node 24 or newer.**
4. **A higher Lambda quota, asked for a day ahead.** A new account allows 10 concurrent Lambda
   executions per region, and Galena's API, detection and background jobs share them in the home
   region. Ask for more in Service Quotas ("Concurrent executions") in your home region, and
   allow a day for AWS to answer.
5. **Your regions**, below. The presets work as they are.
6. Optional: **a domain whose DNS you control**, for the status page and the dashboard (the
   examples use Cloudflare). Without one, both are on CloudFront addresses.
7. Optional: **email**. Notification email needs that domain, and SES production access, which
   AWS also takes about a day to approve.

## Choose your regions

`galena init` offers two presets, `eu` and `us` (see the [CLI](/docs/reference/cli/#galena-init)
for their regions). Galena's own deployment runs `eu`. To change a region, edit
`galena.config.json` before the first deploy: the database lives in the home region, so moving
it later starts an empty deployment there.

**Home region.** The API, the database, detection and the background jobs run here. Pick a region
where the services you watch don't run. If they share one and it fails, detection stops when you
need it most. The status page keeps showing its last snapshot, nothing can change it until the
region is back, and two hours after its last confirmation it says "Status not confirmed since …".
Outside the presets, check that the region offers Aurora Serverless v2 with the RDS Data API,
EventBridge Scheduler and, if you send email, SES. Apart from the subscribe form, visitors to the
status page never reach this region, so pick it for independence, not for their latency.

**Probe regions.** At least three, where your monitors are checked every minute. By default,
detection acts only when two regions agree, so a network problem near one of them doesn't open an
incident on its own. Spread them out, and put them near the people who use your services. A probe
region can also be a page region.

**Page regions.** The status page's buckets: a primary, and a replica that CloudFront switches to
if the primary fails. Both must differ from the home region and from each other, so the page
keeps serving while the home region is down. Visitors load the page from the CloudFront edge
nearest them, which asks the bucket for a file at most every two seconds, so on a busy page most
requests never leave the edge. A primary near most of your visitors makes the rest a little
faster.

CloudFront's certificates for custom domains always live in us-east-1, whatever you pick.

## Two commands

In an empty directory:

```bash
npx @astrlme/galena init
npx @astrlme/galena deploy
```

`init` writes the config, `galena.config.json`, in that directory. `deploy` does everything in the
steps below except the DNS records, which it prints for you to add, and on the first run it asks
for the owner's details. See the [CLI reference](/docs/reference/cli/#galena-deploy) for each step.
Keep the directory: every later command reads the config from it.

Most of the first deploy is AWS creating resources, several stacks at a time; the database takes
longest. With a domain, `deploy` prints each certificate's validation record while it waits for
it: add the record at your DNS host and the deploy carries on.

The package carries Galena's source for its version. Its first run copies that to
`~/.galena/<version>` and installs the dependencies there with pnpm, which corepack provides
(Node 24 includes corepack; on a newer Node, run `npm install --global corepack` first), so the
first command of a version takes longer. Nothing needs Docker or git.

## Upgrading

Each release has its notes in
[CHANGELOG.md](https://github.com/astrlme/galena/blob/main/CHANGELOG.md).
`npx @astrlme/galena doctor` says which version your deployment runs and whether a newer release
is out. Name the release you deploy:

```bash
npx @astrlme/galena@0.2.0 deploy
```

Read the upgrade notes of every release between yours and the new one first; most need nothing.
The database only moves forward, so `deploy` refuses a release older than the one your deployment
runs, and code without the last migration your database ran. Going back means a release at least
as new, or `--force` when you know the older code works on the newer schema.

From a clone of the repository instead, check out the release's tag (`git checkout v0.2.0`), run
`pnpm install --frozen-lockfile`, then the same commands as `pnpm galena <command>` from the
repository root. Deploying from GitHub Actions: the Deploy workflow deploys your fork's `main`, so
move it to the release (merge the tag, or reset `main` to it) and run Deploy. The workflow doesn't
refuse older code; check `pnpm galena doctor` before you run it.

## Appendix: deploying from a fork

The same deployment by hand, or with deploys from GitHub Actions. This path needs a fork of the
repository, and runs the CLI from its root as `pnpm galena <command>`.

<Steps>
<Step>

### Choose regions and names

Run `pnpm install`, then `pnpm galena init` at the repository root. It asks for a name, a region
preset and optional domains, and writes `galena.config.json`. The
file is never committed. Edit it for what `init` doesn't ask, such as deploying from GitHub; see
[Configuration](/docs/reference/configuration/) for every field and the [CLI](/docs/reference/cli/)
for the presets.

| Setting | Meaning |
| --- | --- |
| `homeRegion` | Where the API, the database, detection and the background jobs run. See [Choose your regions](#choose-your-regions). |
| `probeRegions` | At least three regions that run checks. See [Choose your regions](#choose-your-regions). |
| `pageRegions` | The status page's primary and replica regions. The config refuses either one sharing a region with `homeRegion`, or with each other. |
| `github.repository`, `github.oidcSubject` | Your fork. The subject has the form `repo:<owner>@<owner id>/<repo>@<repo id>`; `gh api repos/<owner>/<repo>` shows both ids. |
| `pageDomain` | Optional: the status page's own hostname, for example `status.example.com`. |
| `webDomain` | Optional: the dashboard's own hostname, for example `galena.example.com`. Without it, the dashboard is on its CloudFront address. |
| `email` | Optional: the domain and address notification email is sent from. Without it, email subscriptions are off. |
| `stage` | Your deployment's name, used in every stack and parameter. The steps below use `dev`. |
| `telemetryCapacity` | DynamoDB read and write units. Deployments in one account and region share the free tier of 25 each, and so do the accounts of an AWS Organization. |
| `smoke`, `retainData` | Leave `smoke` out (it's the maintainer's deployed test). `retainData` keeps the table and config bucket if their stack is deleted. |

</Step>
<Step>

### Prepare the account

Set up the account and the AWS CLI as in [Before you start](#before-you-start), then bootstrap
the CDK in every region the stage uses, plus `us-east-1` for CloudFront certificates:

```bash
pnpm --filter @galena/infra exec cdk bootstrap \
  aws://ACCOUNT/eu-central-1 aws://ACCOUNT/eu-west-1 aws://ACCOUNT/eu-west-3 \
  aws://ACCOUNT/eu-north-1 aws://ACCOUNT/us-east-1
```

</Step>
<Step>

### Create the deploy role

Deploy the CI stack once from your machine:

```bash
pnpm --filter @galena/infra exec cdk deploy galena-dev-ci-access
```

It creates GitHub's OIDC provider and the role `galena-dev-github-deploy`. Only workflows on
`refs/heads/main` of your fork can assume it, and it can do nothing but assume the CDK bootstrap
roles. Add its ARN to your fork as the repository variable `AWS_DEPLOY_ROLE_ARN` (Settings,
Secrets and variables, Actions, Variables), and the whole of `galena.config.json` as the variable
`GLN_CONFIG`: the Deploy workflow writes it back to the file.

</Step>
<Step>

### Store the secrets

Three SecureString parameters in the home region, made once and never printed:

| Parameter | Value |
| --- | --- |
| `/galena/dev/auth-secret` | Signs session cookies and encrypts two-factor secrets. 32 random bytes or more. |
| `/galena/dev/app-key` | Exactly 32 random bytes, base64. Seals stored credentials such as Slack URLs and webhook signing secrets, and signs confirmation and unsubscribe links. |
| `/galena/dev/setup-token` | Random. First-run setup must send it, so nobody else can create the owner before you do. |

```bash
aws ssm put-parameter --name /galena/dev/auth-secret --type SecureString \
  --value "$(openssl rand -hex 32)"
aws ssm put-parameter --name /galena/dev/app-key --type SecureString \
  --value "$(openssl rand -base64 32)"
aws ssm put-parameter --name /galena/dev/setup-token --type SecureString \
  --value "$(openssl rand -hex 32)"
```

The API and the background jobs read them when a Lambda container starts. Keep the app key: a new
key makes stored Slack URLs, webhook secrets and old subscription links unreadable.

A fourth, `/galena/dev/slack-app`, is optional: it holds your Slack app's secrets for
[approvals in Slack](/docs/guides/slack-app/). So are `/galena/dev/evaluator-heartbeat` and
`/galena/dev/jobs-heartbeat`, the ping URLs of an
[outside dead-man's switch](/docs/operations/troubleshooting/#outside-heartbeats) that emails you
when Galena stops, even if AWS can't.

</Step>
<Step>

### Deploy

In your fork, open Actions, choose **Deploy**, and run it on `main`. It builds the dashboard,
deploys every stack with `cdk deploy --all`, and ends with a smoke test that signs in as nobody
and expects a 401 through CloudFront, which proves CloudFront, the API and the database all
answer. The API stack runs the database migrations as part of the deploy.

<Callout type="warn">
The workflow deploys the `dev` stage and signs in to `eu-central-1`. If your home region differs,
change `aws-region` in `.github/workflows/deploy.yml` too.
</Callout>

The first run creates, among others:

- `galena-dev-foundation`: the VPC (isolated subnets only), Aurora Serverless v2, DynamoDB,
  the SQS FIFO queues for check results, jobs and HTML builds, and the config bucket.
- `galena-dev-probe-<region>` in each probe region, and `galena-dev-detection` (the evaluator).
- `galena-dev-api` and `galena-dev-web` (the dashboard on CloudFront).
- `galena-dev-page`, `galena-dev-page-replica` and, with a domain, `galena-dev-page-certificate`.
- `galena-dev-dashboard-certificate`, when `webDomain` is set.
- `galena-dev-jobs`: the background jobs and the HTML builder on Lambda, and the recurring
  schedules for the outbox sweep, the uptime rollup and the hourly page heartbeat.
- `galena-dev-email`, when `email` is set.
- `galena-dev-smoke`, on the `dev` stage only: an endpoint the end-to-end Smoke workflow takes
  down and brings back to prove detection and publishing work in AWS. It stays stopped between
  runs.

</Step>
<Step>

### Point DNS at it

With a `pageDomain` or a `webDomain`, for each:

1. Add the certificate's validation CNAME (shown in ACM in `us-east-1`) while the first deploy
   waits for it.
2. Add a CNAME from the domain to its CloudFront distribution's domain: the status page's
   `DistributionDomain` output, or the same output of `galena-dev-web` for the dashboard. With
   Cloudflare, set the records to DNS only.

With `email`:

1. Add the records the `galena-dev-email` stack prints as outputs: three DKIM CNAMEs, the MX and
   SPF records for the MAIL FROM domain, and a DMARC record.
2. Request SES production access in the home region. Until AWS approves it, SES only sends to
   addresses you have verified.

</Step>
<Step>

### Check the deployment

```bash
pnpm galena doctor
```

It reads your account and DNS, changes nothing, and prints one line per check with
what to fix under any that isn't `ok`. See the [CLI reference](/docs/reference/cli/#galena-doctor)
for what each check means.

</Step>
<Step>

### Create the owner

The dashboard's address is the `galena-dev-web` stack's `DashboardUrl` output: your `webDomain`, or
the CloudFront address without one. The API answers on the same origin. First-run setup has no screen yet, so create the workspace and its owner with
one request:

```bash
URL=https://d1234example.cloudfront.net
TOKEN=$(aws ssm get-parameter --name /galena/dev/setup-token --with-decryption \
  --query Parameter.Value --output text)
curl -X POST "$URL/v1/setup" -H 'content-type: application/json' \
  -H "x-galena-setup-token: $TOKEN" -d '{
  "workspaceName": "Acme",
  "name": "Your name",
  "email": "you@example.com",
  "password": "at least twelve characters"
}'
```

It works once, and only with the setup token: without it the API answers 403. After that, sign-up
is closed, and you sign in at `$URL/sign-in/`.

</Step>
</Steps>
