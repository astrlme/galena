| Store | Holds | Written by | Read by |
| --- | --- | --- | --- |
| Aurora Serverless v2 (Postgres 16) | The domain: everything people create, and every confirmed state change | The API, the background jobs | The API, the background jobs |
| DynamoDB `telemetry` | Check results, detection state, heartbeat check-ins | The evaluator and the heartbeat sweeper; the API writes check-ins | The evaluator, the sweeper, the API (for the dashboard) |
| S3 config bucket | `monitors.json` | The background jobs | The probes |
| S3 page buckets | The published status page | The background jobs (primary); S3 replication (replica) | CloudFront |
| SSM Parameter Store | Secrets and resource identifiers | You, and CDK | The API, CDK, you |

## Aurora

Aurora is the source of truth. It runs with a minimum of 0 capacity units and pauses after five
idle minutes; the maximum is set per stage (`auroraMaxAcu`). It sits in isolated subnets and is
reached only through the Data API, authorised by IAM. RDS keeps the master password in Secrets
Manager and rotates it every 7 days.

| Area | Tables |
| --- | --- |
| Identity | `user`, `session`, `account`, `verification`, `two_factor` |
| Workspace | `workspace`, `member`, `audit_log` |
| Page | `page`, `component_group`, `component`, `page_component` |
| Monitors | `monitor`, `monitor_state_change`, `uptime_daily` |
| Incidents | `incident`, `incident_update`, `incident_component`, `timeline_event` |
| Maintenance | `maintenance`, `maintenance_component` |
| Notifications | `subscriber`, `webhook_endpoint`, `delivery` |
| Events | `outbox` |

Conventions:

- ids are UUID v7, generated in the application;
- columns are snake_case, with `created_at` and `updated_at` on every table;
- every table but the identity tables carries `workspace_id`;
- incidents and maintenance windows are soft-deleted, for the record;
- `monitor` holds each monitor's last confirmed state and its sequence number, which only moves
  forward; `monitor_state_change` keeps each transition once, unique on monitor and sequence;
- `uptime_daily` holds the minutes spent in each status, per component per UTC day.

Migrations live in `packages/db/migrations` and run on every deploy from a Lambda in the API
stack.

## DynamoDB

One table, `telemetry`, provisioned inside the always-free tier and without point-in-time
recovery: everything in it can be rebuilt by checking again.

| Item | Partition key | Sort key | Holds |
| --- | --- | --- | --- |
| Check result | `MON#<monitorId>` | `R#<scheduledAt>#<region>` | Status, latency, phases, error; expires after 90 days |
| Hour of one region | `MON#<monitorId>` | `H#<YYYY-MM-DDTHH>#<region>` | Checks by status, the slowest answer, a latency histogram, the mean of each phase; expires after 30 days |
| Day of one region | `MON#<monitorId>` | `D#<YYYY-MM-DD>#<region>` | The same, summed from the day's hours; expires after 400 days |
| Minutes of an hour, of a day | `MON#<monitorId>` | `UH#<YYYY-MM-DDTHH>`, `UD#<YYYY-MM-DD>` | Minutes checked, and minutes a quorum of regions saw the monitor down; expire with their hours and days |
| Summary | `MON#<monitorId>` | `SUMMARY` | The last 24 hours' median per hour and p95, and the last 30 days' minutes checked and down: what the monitors list shows, replaced each hour |
| Monitor state | `MON#<monitorId>` | `STATE` | The detection state, a `version` every write is conditional on, the last minute applied per region, and transitions not yet confirmed as triggered |
| Heartbeat check-in | `MON#<monitorId>` | `PING` | The newest check-in and when the URL it came through was made; an older URL never overwrites a newer one's; expires 400 days after the check-in |
| Check-in for the list | `MON#<monitorId>` | `P#<ISO time>` | One per recorded check-in, for the monitor page's list; expires after 30 days |
| Region health | `REGION#<region>` | `HEALTH` | Whether the region is excluded, and its run of canary passes |

The hour and day items are rollups, written by the hourly `rollup.telemetry` job so a chart never
reads more than it shows: a day's or a week's chart reads hours, and a month's or a quarter's reads
days (90 days of three regions is 270 items). Latency counts answers only, in 50 buckets spaced
evenly on a log scale from 1 ms to 60 s; summed buckets give a day's p95 within about 12% of the
exact one, which averaging 24 hourly p95s can't. Phases keep a sum and a count, so their means add
up to the mean answer. To build the rollups from the checks already stored, run
`pnpm rollups:backfill --stage <name>` once with your AWS credentials. It keeps to two capacity
units a second (`--units`) so probes' writes aren't throttled meanwhile, and if it stops it says
how to go on.

## S3

| Bucket | Notes |
| --- | --- |
| Config | Private. One file, `monitors.json`: enabled monitors and their unfinished maintenance windows, sorted so the same state always writes the same bytes. |
| Page primary | Private, read by CloudFront. Files under `pages/<slug>/`, and the page's internal view under `pages/internal/`, served only on the dashboard's `/internal*` with signed cookies. Versioned for replication; old versions expire after a day. |
| Page replica | The same, in a second region, filled by replication. |
| Dashboard | Private, read by CloudFront. The Next.js static export. |

## SSM parameters

Under `/galena/<stage>/`:

| Parameter | Kind | Set by |
| --- | --- | --- |
| `auth-secret`, `app-key`, `setup-token` | SecureString | You once, or `galena deploy` |
| `evaluator-heartbeat`, `jobs-heartbeat` (optional) | SecureString | You: the ping URLs of an [outside dead-man's switch](/docs/operations/troubleshooting/#outside-heartbeats) |
| `page-signing-key-<generation>` | SecureString | The API stack, once: the key that signs access to the [internal page](/docs/concepts/internal-page/). Never deleted with its stack |
| `public-url` | String | The web stack: the dashboard's address |
| `database-cluster-arn`, `database-secret-arn`, `telemetry-table`, `check-results-queue-url`, `check-results-queue-arn`, `config-bucket`, `alarm-topic-arn` | String | The foundation stack |
