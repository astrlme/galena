---
title: Troubleshooting
description: What to check when something doesn't happen.
---

Most problems show up in one of three places: CloudWatch Logs (the jobs log
`/galena/<stage>/jobs` has a line for every job run, the HTML builder's is
`/galena/<stage>/builder`, and every other Lambda has its own, all kept a month), the alarms
below, and the dashboard's own error messages, which name what to do.

The CloudWatch dashboard `galena-<stage>` in the home region shows the trend behind the alarms:
checks in each probe region, check results sent, the evaluator's errors, throttles and
transitions, how long the oldest message in each queue has waited, dead letters (where a job that
failed for good ends up), job crashes and heartbeat runs, API requests and latency, and Aurora's
capacity. It adds no custom metrics, and it is one of the three dashboards the free tier covers.

## Alarms

Thirteen CloudWatch alarms in the home region publish to the SNS topic `galena-<stage>-alarms`:

| Alarm | Fires when |
| --- | --- |
| Dead letters | A check result failed five times and waits in the dead-letter queue |
| No check results | No probe region sent a result for 10 minutes |
| Evaluator errors | The evaluator failed in two 5-minute periods in a row |
| Evaluator throttles | Lambda throttled the evaluator, so the account ran out of concurrency |
| Job or build dead letters | A job or an HTML build failed its last attempt and waits in its dead-letter queue |
| Jobs or builds waiting | A job or an HTML build has waited over 15 minutes: a lane is stuck or its function can't start |
| Undelivered schedules | Scheduler couldn't deliver a job for later or a recurring job within an hour |
| No heartbeat | `page.heartbeat` hasn't run for two hours |
| Database awake | Aurora has been awake for 4 hours in a row: something keeps querying it |
| API traffic | The API answered over 5,000 requests in an hour: look for unexpected callers |
| Untriggered jobs | The API couldn't start a job, so a saved change waits for the outbox sweep, up to six hours: check SQS and Scheduler, and the API's log for the reason |

Nothing subscribes to the topic in code, so no address is kept in your fork. Subscribe one once,
then confirm the email AWS sends:

```bash
aws sns subscribe --region <home region> --protocol email --notification-endpoint you@example.com \
  --topic-arn "$(aws ssm get-parameter --region <home region> --name /galena/dev/alarm-topic-arn --query Parameter.Value --output text)"
```

## Outside heartbeats

The alarms run in the same AWS account as everything they watch. If the account, CloudWatch or
the email path stops, they stop too, and nothing says so. An outside dead-man's switch covers
that: Galena pings it while it works, and the service emails you when the pings stop.

Galena pings two URLs, each optional:

| Parameter | Pinged | Set the check to |
| --- | --- | --- |
| `/galena/dev/evaluator-heartbeat` | By the evaluator, at most once a minute while it evaluates check results | Period 1 minute, grace 4 minutes |
| `/galena/dev/jobs-heartbeat` | After each hourly `page.heartbeat` run | Period 1 hour, grace 1 hour |

The evaluator runs only when probes send results, so its check needs at least one monitor. Any
service that takes a plain `GET` to a ping URL works. [Healthchecks.io](https://healthchecks.io/)
does on its free plan, and is open source if you'd rather run it yourself.

1. Create the two checks with the periods above, and copy each one's ping URL.
2. Store each URL as a SecureString in the home region. Anyone who has the URL can keep the
   check quiet, so treat it as a secret:

   ```bash
   aws ssm put-parameter --region <home region> --name /galena/dev/evaluator-heartbeat \
     --type SecureString --value "https://hc-ping.com/<uuid>"
   aws ssm put-parameter --region <home region> --name /galena/dev/jobs-heartbeat \
     --type SecureString --value "https://hc-ping.com/<uuid>"
   ```

3. The evaluator and the jobs read their URL when a Lambda container starts. Store the URLs
   before your first deploy and the pings start with it. On a running deployment, a deploy
   that changes nothing starts no new containers, so start them yourself:

   ```bash
   for fn in $(aws lambda list-functions --region <home region> --output text --query \
     "Functions[?starts_with(FunctionName, 'galena-dev-detection-Evaluator') || starts_with(FunctionName, 'galena-dev-jobs-Jobs')].FunctionName"); do
     aws lambda update-function-configuration --region <home region> --function-name "$fn" \
       --description "Heartbeat URL read $(date -u +%FT%TZ)" > /dev/null
   done
   ```

   `galena doctor` warns while either URL is missing.

A ping that fails is logged as `heartbeat ping failed` and never fails the work it follows.

## The first request is slow

Aurora pauses after five idle minutes. The first request afterwards waits about 15 seconds while
it resumes; the dashboard says so after 10 seconds. This is expected and is what keeps an idle
deployment cheap. Scripts calling the API should allow at least 20 seconds.

## The page didn't update

1. In the jobs log, find the `outbox.dispatch` line for the change. If there is none, the API
   couldn't reach the job queue when you saved: the API's log says `outbox.dispatch was not
   triggered`. The change is saved and its event is still pending; `outbox.sweep` dispatches it
   within six hours, or save the change again to publish sooner.
2. Check the `page.publish` line that followed. `superseded` means a newer publish already covered
   the change.
3. Check the builder's log in CloudWatch (stack `galena-<stage>-jobs`) for the HTML: each build
   logs `page.rebuild-html` with its outcome. The data files (`snapshot.json`) land first, so an
   open page updates within 30 seconds even before the HTML does.

## A monitor isn't being checked

- Is it paused? Paused monitors leave `monitors.json`.
- After adding or changing a monitor, `outbox.dispatch` rewrites `monitors.json`; the probes pick
  it up on their next run.
- The probes' log groups (`galena-<stage>-probe-<region>`) show each run; a check aimed at a
  private address fails with `blocked_by_guard`.

## A monitor stays Unknown

Detection waits until at least `quorum` regions have a verdict, which takes a couple of checks
per region. A monitor that stays unknown longer usually has regions that only return `error`
(the probe failing, not the target), or a region excluded because its canary fails. The
dashboard's per-region results show which.

## A monitor shows Flapping

It changed state more than four times in 30 minutes. It leaves flapping once it stays up for 30
minutes, or down for 15. If the endpoint really is unstable, that is the truth; if the checks are
too strict, give it a longer timeout or a higher `failThreshold`.

## Emails don't arrive

- Until AWS grants SES production access, SES only sends to addresses verified in SES.
- Without `email` in the deployment config, Galena sends no email and the subscribe form is
  off.
- An address that bounced or complained is suppressed for good; the dashboard shows "Stopped: the
  address bounced or reported spam".
- Check the `notify.email` line in the jobs log and its delivery row's `last_error`.

## A webhook endpoint shows Failing

A delivery failed after its last attempt: the dashboard shows since when, and **Deliveries**
shows the receiver's last answer to each notice. **Send test** shows what it answers now. A 4xx
other than 429 is not tried again; fix the receiver, then send the failed deliveries again. After
3 days of failures the endpoint is turned off; **Turn on** sends a test and turns it back on once
the receiver accepts it.

## The page says "Status not confirmed"

The page hasn't been confirmed for two hours, though `page.heartbeat` should confirm it every hour.
Check its lines in the jobs log and the No heartbeat alarm. A run that answered `rollup` read
the database, so a paused or unreachable Aurora shows up there.

## The internal page isn't available

The API couldn't read the key that signs access to the internal page, the SecureString
`/galena/<stage>/page-signing-key-<generation>`. Its log says why: usually the parameter was
deleted. A deploy doesn't make a lost key again, because CloudFront can't take a new public key in
place. Raise `pageKeyGeneration` in the deployment's config and deploy: that makes a new key under
a new name, and members open the page again from the dashboard. Raising it also rotates a key you
no longer trust.

## The internal page answers 403

Its access ends 12 hours after a member opened it from the dashboard, and at sign-out. Open
**Internal page** in the dashboard again; bookmark that link, not the page itself.

## `403 not_through_cloudfront`

The API only answers requests that came through CloudFront. Call it on the dashboard's address,
not the API Gateway URL.
