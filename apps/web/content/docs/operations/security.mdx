## Ways in

<Diagram name="trust" />

| Entry | Who | Protected by |
| --- | --- | --- |
| Status page | Anyone | Static files only. HSTS, `X-Frame-Options: DENY`, a content security policy with hashed scripts |
| `/public/*` on the page's domain | Anyone | Subscribe, confirm and unsubscribe only; rate limits; answers that never reveal whether an address is subscribed |
| `/internal*` on the dashboard's domain | Members | Static files only. CloudFront signed cookies, set by the API after sign-in, for 12 hours; sign-out expires them |
| Dashboard and `/v1/*` | Members and their API keys | Session cookies from Better Auth or scoped API keys, role checks on every route, a content security policy, CloudFront in front |
| `/auth/*` | Anyone | Better Auth: password hashing, TOTP two-factor, rate limits |
| `/hooks/*` | Alert sources | A signed token in the URL, checked without the database; at most 120 alerts per integration a minute |
| API Gateway directly | Nobody | Refused unless a secret header that only CloudFront adds is present |
| AWS | The deploy role, the Lambdas and their roles | IAM, each scoped to exactly what it needs |

### The origin secret

The API Lambda sits behind API Gateway, which has a public address of its own. CloudFront adds a
random header, `x-galena-origin`, to every request it forwards; the value lives in Secrets Manager
and the API compares it in constant time. Anything that skips CloudFront, including attempts to
forge the visitor's address, is refused with `403`. Only `/health` answers without it.

### Rate limits

API Gateway limits each path open to anyone (`/auth/*`, `/public/*`, `/hooks/*`, `/slack/*`)
below the API's overall rate. Behind that, Better Auth limits sign-in and other auth requests per
visitor address. Its counters are kept in each API instance's memory, not the database, so a
flood of sign-in attempts can't keep Aurora awake. The address comes from CloudFront's
`CloudFront-Viewer-Address` header, which a visitor can't set, and reaches the API in a header
the API sets itself. The subscribe form has its own limits; see [Limits](/docs/reference/limits/).

### What keeps the bill small

Aurora awake is most of a deployment's bill. Where it can, Galena refuses a request with no valid
credential before any query:

- A session cookie is checked against its signature first.
- An API key carries a tag keyed with the app key; a key this deployment didn't make is refused
  first.
- A hook URL's token is signed. A replaced or deleted URL is refused within a minute, for at most
  one lookup a minute.
- Sign-in endpoints the dashboard doesn't use, such as sign-up and password reset, are answered
  before Better Auth runs.

Two kinds of request still reach the database for anyone: a sign-in attempt, and a subscribe-form
post with a well-formed address. They are throttled and limited per visitor address, not
prevented, so a slow, steady stream of them can keep Aurora awake. The **Database awake** alarm
says so after 4 hours, and the **API traffic** alarm after 5,000 requests in an hour.

The per-path throttles are shared by everyone calling that path, so a flood also holds back real
sign-ins, sign-ups or alerts until it stops. There is no WAF: it costs more than a small
deployment's whole budget.

Inside the workspace, the limits keep a mistake, a stolen key or a flapping alert from
multiplying the bill: at most 50 monitors, and 50 destinations, integrations and API keys; at
most 30 notices an hour to subscribers and destinations; at most 20 test messages and resends a
minute.

### Sign-up

Only first-run setup creates an account. In AWS it needs the setup token, a SecureString only
someone with access to the AWS account can read, so nobody can claim a fresh deployment first.
After the workspace exists, every attempt to create a user is refused in a database hook,
whatever route it comes through.

## Outbound requests

Every outbound URL (monitor checks, Slack, webhooks, the canary) passes the SSRF guard:

- only `http://` and `https://`, and no credentials in the URL;
- the host's addresses are checked before the request, then again as the socket connects, so a
  name can't be re-pointed at a private address in between (DNS rebinding);
- loopback, private, link-local (which includes the instance metadata service), carrier-grade
  NAT, multicast, documentation and other special-purpose ranges are refused, in IPv4 and IPv6,
  including IPv4 addresses embedded in IPv6 ones;
- every redirect hop is checked again.

## Secrets and keys

| Secret | Where | Used for |
| --- | --- | --- |
| Auth secret | SSM SecureString | Better Auth: signing session cookies and encrypting two-factor secrets |
| App key | SSM SecureString, read by the API and the jobs | See below |
| Database credentials | Secrets Manager, rotated by RDS every 7 days | The Data API |
| Origin secret | Secrets Manager, replicated to the page region | CloudFront and the API |
| Page signing key | SSM SecureString, made by the first deploy | Signing the internal page's cookies; CloudFront holds only the public half |

The **app key** is 32 random bytes. Galena never uses it directly; it derives a separate key for
each purpose with HKDF-SHA256, so no key can stand in for another:

<Diagram name="keys" />

| Derived key | Protects |
| --- | --- |
| `seal` | Slack webhook URLs and webhook signing secrets, encrypted with AES-256-GCM before they are stored. The API never returns them. |
| `link` | Confirm and unsubscribe links: an HMAC-SHA256 over the purpose, the subscriber and the time. Nothing about a link is stored. |
| `hash` | The addresses of visitors who use the subscribe form, kept only as keyed hashes for its rate limits; the tag that makes an API key this deployment's |

Secrets never appear in code, logs, snapshots or error messages. Webhook signing secrets are
shown once, when the endpoint is created.

## Personal data

- Subscriber email addresses are visible only to admins, and only masked (`a***@example.com`).
- The subscribe form keeps visitors' IP addresses only as keyed hashes. Better Auth records a
  member's IP address on each session, and keys its sign-in rate limits by address.
- The public status page and its files contain public information only: nothing from a draft,
  dismissed or internal incident. The internal page, behind sign-in, adds internal incidents
  and internal-only monitors; nothing from a draft or a dismissed incident.

## Infrastructure

- No NAT gateway and no Lambda in a VPC; Aurora sits in isolated subnets and is reached only
  through the Data API with IAM.
- Buckets are private, encrypted, and refuse plain HTTP; CloudFront reads them through origin
  access control.
- Every stack passes cdk-nag's AWS Solutions rules, with each exception explained in code.
- GitHub Actions deploys through OIDC: no AWS keys are stored in GitHub, and the deploy role
  trusts only `main` of one repository, by its immutable ids.
- Third-party actions are pinned to commit SHAs, installs use the frozen lockfile, and only
  `esbuild` may run an install script.

## Reporting a vulnerability

Report privately through the repository's **Security** tab, **Report a vulnerability**. See
